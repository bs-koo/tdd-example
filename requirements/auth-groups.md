# 로그인 · 그룹 · 그룹 전용 회의실 — 요구사항

- **문서 버전**: 1.0
- **작성일**: 2026-09-01
- **선행 문서**: [`mvp.md`](mvp.md) — 이 문서는 MVP를 대체하지 않고 **확장**한다
- **스택**: 변경 없음 (Spring Boot 4.1.1 / Java 21 / React 19 / TypeScript 7)

## 1. 무엇이 달라지는가

MVP는 인증이 없었다(`mvp.md` NFR-05). 예약자를 **문자열 이름**으로만 식별했으므로, 이름만 알면 남의 예약을 취소할 수 있었고 회의실 4개는 전사가 공유하는 전역 자원이었다.

이 확장은 세 가지를 바꾼다.

1. **로그인** — 이메일·비밀번호로 가입하고 로그인한다. 이후 모든 예약 관련 요청은 인증을 요구한다.
2. **그룹** — 사용자는 그룹을 만들고 이메일로 다른 사용자를 초대한다. 초대받은 사람이 **수락해야** 그룹원이 된다.
3. **그룹 소유 회의실** — 회의실은 전역 자원이 아니라 그룹에 속한다. **승인된 그룹원만** 그 그룹에 회의실을 추가하고 예약할 수 있다.

### 1.1 MVP 규칙 중 바뀌는 것

| 원 규칙 | 변경 |
|---------|------|
| BR-07 예약 취소는 예약자 본인만 — **예약자명 일치**로 검증 | **회원 id 일치**로 검증한다. 동명이인이 남의 예약을 취소할 수 없다 |
| NFR-05 인증 없음 | 폐기. Bearer 토큰 인증을 도입한다 |
| 회의실 4개 고정 시드 | 사용자가 그룹 안에서 회의실을 추가한다. 시드는 개발·시연용 데모 데이터로만 남는다 |
| `GET /api/rooms` 전체 목록 | 폐기. 회의실은 항상 그룹 문맥(`GET /api/groups/{id}/rooms`)에서 조회한다 |

BR-01~BR-06, BR-08(겹침·30분 단위·영업시간·길이·과거 금지·14일 제한·중복 취소 금지)은 **그대로 유지**한다.

## 2. 도메인 규칙

| ID | 규칙 | 비고 |
|----|------|------|
| AR-01 | 이메일은 계정을 식별하는 유일 키다. 대소문자와 앞뒤 공백을 무시해 하나로 접는다 | `BonSeung@SQI.com` 과 `bonseung@sqi.com` 은 같은 계정 |
| AR-02 | 비밀번호는 8자 이상 64자 이하다 | 앞뒤 공백도 의미 있는 문자로 센다 |
| AR-03 | 비밀번호는 평문으로 저장하지 않는다 | PBKDF2-HMAC-SHA256, 계정마다 다른 솔트 |
| AR-04 | 로그인 실패 사유는 구분해 알리지 않는다 | 미가입 이메일과 비밀번호 불일치가 같은 `INVALID_CREDENTIALS` |
| AR-05 | 세션 토큰은 12시간 후 만료된다 | 만료 시각 **정각은 이미 만료**로 본다 |
| AR-06 | 로그아웃은 그 토큰만 무효화한다 | 다른 기기의 세션은 유지된다 |
| GR-01 | 그룹을 만든 사람은 즉시 그 그룹의 OWNER이자 APPROVED 상태다 | 자기 그룹에 자기가 승인 요청을 하지 않는다 |
| GR-02 | 초대는 **그룹장만** 보낼 수 있다 | 승인된 일반 그룹원도 초대 권한이 없다 |
| GR-03 | 초대는 PENDING 상태의 멤버십이다 | 초대장과 멤버십을 따로 두지 않는다 |
| GR-04 | 초대받은 본인만 수락·거절할 수 있다 | 그룹장도 대신 수락할 수 없다 |
| GR-05 | 이미 응답한 초대에는 다시 응답할 수 없다 | 멱등이 아니라 거절 |
| GR-06 | 이미 초대했거나 참여 중인 사람은 다시 초대할 수 없다 | `ALREADY_INVITED` |
| GR-07 | **거절한 사람은 다시 초대할 수 있다** | 새 멤버십을 만들지 않고 기존 것을 PENDING으로 되돌린다 |
| GR-08 | 자기 자신은 초대할 수 없다 | `SELF_INVITATION` |
| GR-09 | 가입하지 않은 이메일은 초대할 수 없다 | `MEMBER_NOT_FOUND`. 이 MVP에는 메일 발송이 없다 |
| RR-01 | 회의실은 정확히 하나의 그룹에 속한다 | 그룹 간 회의실 공유는 범위 밖 |
| RR-02 | **승인된 그룹원만** 그 그룹에 회의실을 추가할 수 있다 | 대기·거절·무관한 사람 모두 거절 |
| RR-03 | **승인된 그룹원만** 그 그룹의 회의실을 조회·예약할 수 있다 | 남의 그룹 회의실은 존재해도 쓸 수 없다 |
| RR-04 | 회의실 이름·위치는 1~30자, 수용 인원은 1~999명이다 | 이름과 위치는 trim 후 길이를 잰다 |

### 2.1 권한 판정 순서 (고정)

여러 오류가 동시에 성립할 때 어떤 코드가 나가는지는 **요청마다 흔들리면 안 된다**. 다음 순서로 고정한다.

**회의실 추가** — 인증 → 그룹 존재 → 그룹 권한 → 입력 검증(이름 → 인원 → 위치)

> 권한이 입력 검증보다 **앞선다**. 남의 그룹에 대고 이름 길이를 캐낼 수 없어야 한다.

**예약 생성** — 인증 → 날짜 파싱 → 목적 길이·시간 규칙 → 회의실 존재 → 그룹 권한 → 시간 겹침

> 여기서는 시간 규칙이 권한보다 **앞선다**. 이는 MVP의 검증 순서(`mvp.md` 4.1)를 그대로 유지하기 위한 선택이며, 회의실이 없거나 권한이 없어도 잘못된 시각은 먼저 지적한다.

**예약 취소** — 인증 → 예약 존재 → 본인 여부 → 이미 취소 여부

> 본인 확인이 상태 검사보다 앞선다(MVP와 동일). 남의 예약이 취소됐는지 여부를 알 수 없어야 한다.

### 2.2 멤버십 상태 전이

```
                 (그룹 생성)
                      └──────────────► APPROVED(OWNER)

  (초대)                    (수락)
    └──► PENDING ─────────────────────► APPROVED(MEMBER)
             │
             │ (거절)
             ▼
         REJECTED ──────(재초대)──────► PENDING
```

`APPROVED` 에서 나가는 전이는 없다 — 탈퇴·강퇴는 이 범위에 없다.

## 3. 데이터 모델

### 3.1 Member (회원) — `app_member`

| 필드 | 타입 | 비고 |
|------|------|------|
| id | Long | IDENTITY |
| email | String | **unique**. 정규화된 소문자 |
| name | String | 표시 이름. 1~20자 |
| passwordHash | String | `반복횟수:솔트:해시` |
| createdAt | LocalDateTime | |

### 3.2 Session (세션) — `auth_session`

| 필드 | 타입 | 비고 |
|------|------|------|
| token | String | **PK**. 256비트 난수의 URL-safe Base64 |
| memberId | Long | |
| issuedAt / expiresAt | LocalDateTime | `expiresAt = issuedAt + 12h` |

### 3.3 Group (그룹) — `user_group`

`GROUP` 이 SQL 예약어라 테이블명이 `user_group` 이다.

| 필드 | 타입 | 비고 |
|------|------|------|
| id | Long | IDENTITY |
| name | String | 1~30자 |
| ownerId | Long | 그룹장 회원 id |
| createdAt | LocalDateTime | |

### 3.4 GroupMembership (멤버십) — `group_membership`

| 필드 | 타입 | 비고 |
|------|------|------|
| id | Long | IDENTITY. **초대 id로도 쓰인다** |
| groupId / memberId | Long | 한 쌍은 그룹당 하나만 존재한다 |
| role | enum | `OWNER` / `MEMBER` |
| status | enum | `PENDING` / `APPROVED` / `REJECTED` |
| invitedAt / respondedAt | LocalDateTime | 재초대 시 `respondedAt` 은 null 로 되돌아간다 |

### 3.5 Room (회의실) — 변경분

`groupId`(Long, not null)가 추가되고, id가 시드 고정값에서 **IDENTITY**로 바뀐다.

### 3.6 Reservation (예약) — 변경분

`memberId`(Long)가 추가된다. `reserverName` 은 **표시용으로만** 남고 권한 판정에 쓰지 않는다.

## 4. 오류 코드

MVP의 13종에서 `INVALID_RESERVER_NAME` 을 **제거**(예약자명이 더 이상 요청 필드가 아니다)하고, 회의실 3종 + 인증 7종 + 그룹 9종을 추가해 총 **31종**이 된다. 전체 목록과 HTTP 상태 매핑은 `ErrorCodeHttpStatusTest` 가 전수 검증한다.

오류 응답 형식은 MVP와 동일하다.

```json
{ "code": "NOT_GROUP_MEMBER", "message": "승인된 그룹원만 할 수 있는 작업입니다." }
```

## 5. 인증 방식

로그인하면 **불투명 토큰**(opaque token)을 받아 이후 `Authorization: Bearer <token>` 헤더로 보낸다.

JWT를 쓰지 않은 이유는 이 규모에서 서버 상태를 없앨 이득이 없고, 토큰에 권한을 실으면 **로그아웃과 권한 변경이 즉시 반영되지 않기** 때문이다. 토큰은 세션 테이블을 가리키는 무의미한 난수이며, 권한은 매 요청 DB에서 다시 읽는다.

Spring Security를 도입하지 않았다. 필요한 것이 "헤더의 토큰으로 회원을 찾아 컨트롤러에 넘기는 것" 하나뿐이라, `HandlerMethodArgumentResolver` 하나(`@LoginMember`)로 충분하다. 인증이 반드시 **바디 파싱보다 먼저** 판정되도록 `@LoginMember` 파라미터를 컨트롤러 메서드의 **첫 번째 자리**에 둔다.
