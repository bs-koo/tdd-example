- **스택**: Spring Boot **4.1.1** (Java 21) + React **19** (TypeScript)

## 1. 개요

### 1.1 목적

사내 회의실을 날짜별로 조회하고 예약·취소하는 최소 기능 서비스.

이 문서는 `/gx-tdd` 파이프라인(PRD → 설계 → RED-GREEN-REFACTOR → 리뷰 → verify → 커밋)의 시연 대상이다. 따라서 요구사항을 **판정 가능한 도메인 규칙** 중심으로 기술한다. "저장하면 저장된다" 수준의 요구사항은 RED 단계에서 쓸 실패 테스트가 나오지 않으므로 의도적으로 배제했다.

### 1.2 범위

회의실 목록 조회, 날짜별 예약 현황 조회, 예약 생성, 예약 취소. 로그인·알림·반복 예약은 제외한다 ([8. MVP 이후](#8-mvp-이후)).

### 1.3 성공 기준

1. 회의실 A에 09:00~10:00 예약이 있을 때, 09:30~10:30 요청이 **거절**된다.
2. 같은 상황에서 10:00~11:00 요청은 **허용**된다.
3. 예약자 본인이 아닌 이름으로 취소를 시도하면 **거절**된다.
4. 위 세 가지가 모두 단위 테스트로 검증되고, 화면에서 동일하게 동작한다.

## 2. 도메인 규칙

이 절이 이 서비스의 핵심이다. 아래 규칙은 전부 순수 로직으로 판정 가능하며, 각각이 하나의 RGR 사이클 단위가 된다.

| ID | 규칙 | 비고 |
|----|------|------|
| BR-01 | 같은 회의실에서 시간이 **겹치는** 예약은 생성할 수 없다 | 겹침 정의는 2.1 |
| BR-02 | 예약 시각은 **30분 단위**여야 한다 | 09:00, 09:30 허용 / 09:15 거절 |
| BR-03 | 예약 가능 시간대는 **09:00 ~ 18:00** 이다 | 종료가 18:00인 것은 허용 |
| BR-04 | 예약 길이는 최소 **30분**, 최대 **4시간** 이다 | 경계 포함 |
| BR-05 | **과거 시각**으로는 예약할 수 없다 | 기준: 요청 시점 |
| BR-06 | 오늘로부터 **14일 이내**만 예약할 수 있다 | 15일째 거절 |
| BR-07 | 예약 취소는 **예약자 본인**만 할 수 있다 | 예약자명 일치 검증 |
| BR-08 | 이미 취소된 예약은 다시 취소할 수 없다 | 멱등이 아니라 거절 |

### 2.1 겹침(overlap)의 정의

예약 구간을 **반개구간 `[start, end)`** 로 다룬다. 즉 **끝시각과 시작시각이 같은 두 예약은 겹치지 않는다.**

> 두 구간 A, B가 겹친다 ⟺ `A.start < B.end && B.start < A.end`

이 정의를 채택하는 이유는, 09:00~10:00 회의 직후 10:00~11:00 회의를 잡는 것이 현실에서 정상이기 때문이다.

**판정표** — 기존 예약이 `09:00~10:00`일 때:

| # | 요청 구간 | 관계 | 기대 결과 |
|---|-----------|------|-----------|
| 1 | 08:00~09:00 | 직전에 접함 | ✅ 허용 |
| 2 | 08:30~09:30 | 뒤쪽 부분 겹침 | ❌ 거절 |
| 3 | 09:00~10:00 | 완전 동일 | ❌ 거절 |
| 4 | 09:15~09:45 | 기존에 포함됨 | ❌ 거절 (단 BR-02로도 거절) |
| 5 | 09:30~10:00 | 기존에 포함됨 | ❌ 거절 |
| 6 | 08:30~10:30 | 기존을 포함함 | ❌ 거절 |
| 7 | 09:30~10:30 | 앞쪽 부분 겹침 | ❌ 거절 |
| 8 | 10:00~11:00 | 직후에 접함 | ✅ 허용 |
| 9 | 11:00~12:00 | 완전히 분리 | ✅ 허용 |

**다른 회의실이면 시간이 겹쳐도 허용된다.** 겹침 검사는 항상 같은 `roomId` 안에서만 수행한다.
**취소된 예약은 겹침 검사에서 제외한다.**

## 3. 데이터 모델

### 3.1 Room (회의실)

| 필드 | 타입 | 설명 |
|------|------|------|
| id | Long | PK |
| name | String | 회의실명 (예: "대회의실") |
| capacity | int | 수용 인원 |
| location | String | 위치 (예: "3층") |

MVP에서 회의실은 **고정 시드 데이터**다. 회의실 CRUD는 만들지 않는다.

### 3.2 Reservation (예약)

| 필드 | 타입 | 설명 |
|------|------|------|
| id | Long | PK |
| roomId | Long | 회의실 FK |
| reserverName | String | 예약자명 (1~20자, 필수) |
| purpose | String | 회의 목적 (0~50자) |
| startAt | LocalDateTime | 시작 (30분 단위) |
| endAt | LocalDateTime | 종료 (30분 단위, exclusive) |
| status | Enum | `ACTIVE` / `CANCELLED` |
| createdAt | LocalDateTime | 생성 시각 |

취소는 **삭제가 아니라 상태 변경**이다. 이력이 남아야 BR-08을 검증할 수 있다.

## 4. API 명세

Base path: `/api`

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/rooms` | 회의실 전체 목록 |
| GET | `/rooms/{roomId}/reservations?date=YYYY-MM-DD` | 해당 회의실의 특정 날짜 예약 목록 (ACTIVE만) |
| POST | `/reservations` | 예약 생성 |
| POST | `/reservations/{id}/cancel` | 예약 취소 |

### 4.1 POST /api/reservations

```json
{
  "roomId": 1,
  "reserverName": "김본승",
  "purpose": "주간 회의",
  "startAt": "2026-08-25T09:00:00",
  "endAt": "2026-08-25T10:00:00"
}
```

- 성공: `201 Created` + 생성된 예약
- 규칙 위반: `409 Conflict` (BR-01) / `400 Bad Request` (BR-02~06)

### 4.2 POST /api/reservations/{id}/cancel

```json
{ "reserverName": "김본승" }
```

- 성공: `204 No Content`
- 예약자 불일치: `403 Forbidden` (BR-07)
- 이미 취소됨: `409 Conflict` (BR-08)
- 없는 예약: `404 Not Found`

### 4.3 오류 응답 형식

```json
{ "code": "OVERLAPPING_RESERVATION", "message": "해당 시간대에 이미 예약이 있습니다." }
```

| code | HTTP | 대응 규칙 |
|------|------|-----------|
| `OVERLAPPING_RESERVATION` | 409 | BR-01 |
| `INVALID_TIME_UNIT` | 400 | BR-02 |
| `OUTSIDE_BUSINESS_HOURS` | 400 | BR-03 |
| `INVALID_DURATION` | 400 | BR-04 |
| `PAST_DATETIME` | 400 | BR-05 |
| `TOO_FAR_IN_FUTURE` | 400 | BR-06 |
| `NOT_RESERVER` | 403 | BR-07 |
| `ALREADY_CANCELLED` | 409 | BR-08 |
| `RESERVATION_NOT_FOUND` | 404 | 없는 예약 |
| `ROOM_NOT_FOUND` | 404 | 없는 회의실 |

## 5. 기능 요구사항

### FR-01 · 회의실 목록 조회

- [ ] `GET /api/rooms`가 시드된 회의실 전체를 반환한다
- [ ] 각 항목에 id, name, capacity, location이 포함된다

### FR-02 · 날짜별 예약 현황 조회

- [ ] `GET /api/rooms/{roomId}/reservations?date=2026-08-25`가 해당 날짜의 예약만 반환한다
- [ ] 취소된(`CANCELLED`) 예약은 결과에서 제외된다
- [ ] 예약이 없으면 빈 배열을 반환한다 (404가 아니다)
- [ ] `date` 형식이 잘못되면 400을 반환한다

### FR-03 · 예약 생성

- [ ] 규칙 BR-01~BR-06을 모두 통과하면 201과 함께 예약이 생성된다
- [ ] [2.1 판정표]의 9개 케이스가 표대로 동작한다
- [ ] 다른 회의실이면 시간이 겹쳐도 생성된다
- [ ] 취소된 예약과는 시간이 겹쳐도 생성된다
- [ ] 예약자명이 비어 있으면 400을 반환한다
- [ ] 존재하지 않는 roomId면 404를 반환한다

### FR-04 · 예약 취소

- [ ] 예약자명이 일치하면 204와 함께 상태가 `CANCELLED`로 바뀐다
- [ ] 예약자명이 다르면 403이고 상태는 그대로다
- [ ] 이미 취소된 예약이면 409를 반환한다
- [ ] 취소 후 해당 시간대에 새 예약을 만들 수 있다

### FR-05 · 예약 화면

- [ ] 날짜 선택기와 회의실별 타임슬롯 그리드(09:00~18:00, 30분 단위)가 보인다
- [ ] 예약된 슬롯에는 예약자명과 목적이 표시된다
- [ ] 빈 슬롯을 클릭하면 예약 폼이 열리고, 시작 시각이 채워진 채로 시작한다
- [ ] 서버가 규칙 위반으로 거절하면, 오류 코드에 대응하는 한국어 메시지를 보여준다
- [ ] 예약된 슬롯을 클릭하면 취소 확인을 거쳐 취소를 요청한다

## 6. 비기능 요구사항

| ID | 항목 | 요구 |
|----|------|------|
| NFR-01 | 저장소 | H2 인메모리. 재기동 시 시드 데이터로 초기화된다 |
| NFR-02 | 시간대 | 서버·클라이언트 모두 `Asia/Seoul` 고정 |
| NFR-03 | 시각 주입 | 도메인 로직은 `Clock`을 주입받는다. BR-05·BR-06을 고정 시각으로 테스트하기 위함이다 |
| NFR-04 | 동시성 | MVP에서는 다루지 않는다. 단일 사용자 조작을 전제한다 |
| NFR-05 | 인증 | 없음. 예약자명 문자열로만 식별한다 |

**NFR-03은 타협하지 않는다.** `LocalDateTime.now()`를 도메인 안에서 직접 부르면 BR-05·BR-06 테스트가 실행 시각에 따라 흔들린다. 이건 TDD 시연에서 가장 먼저 드러나는 설계 결함이므로 처음부터 `Clock`으로 간다.

## 7. 구조 및 테스트 전략

### 7.1 백엔드 계층

```
domain/
  TimeSlot          시작·종료를 감싼 값 객체. overlaps() 판정을 여기서 한다
  Reservation       예약 엔티티. cancel(name) 규칙을 스스로 지킨다
  Room              회의실 엔티티
  ReservationPolicy BR-02~BR-06 검증. Clock 주입
application/
  ReservationService  Repository 인터페이스에만 의존
  ReservationRepository (interface)
api/
  ReservationController / RoomController
  GlobalExceptionHandler  도메인 예외 → 4.3 오류 응답
infra/
  JpaReservationRepository
```

핵심은 **`TimeSlot.overlaps()`와 `ReservationPolicy`가 Spring도 DB도 모른다**는 점이다. 이 둘은 `new`로 만들어 즉시 단위 테스트할 수 있고, RGR 사이클이 가장 빠르게 도는 지점이다.

### 7.2 테스트 계층

| 계층 | 도구 | 대상 |
|------|------|------|
| 단위 | JUnit 5 + AssertJ | `TimeSlot.overlaps()` — 2.1 판정표 9케이스를 `@ParameterizedTest`로 |
| 단위 | JUnit 5 + AssertJ | `ReservationPolicy` — BR-02~BR-06 경계값, `Clock.fixed()` 사용 |
| 단위 | JUnit 5 + Fake | `ReservationService` — InMemory Repository로 격리. BR-01, BR-07, BR-08 |
| 통합 | `@SpringBootTest` + MockMvc | API 상태코드와 오류 코드 매핑 |
| 프론트 | Vitest | 슬롯 그리드 렌더링, 오류 코드 → 메시지 변환 |

### 7.3 구현 Phase

RGR 사이클을 아래 8개 Phase로 나눈다. Phase 0은 도메인 규칙이 없는 뼈대 작업이라 RGR 대상이 아니고, Phase 1~4가 이 프로젝트의 핵심 RGR 구간이다. Phase 5~7은 이미 검증된 로직을 감싸는 통합 작업이라 실패 테스트보다 통합 테스트 비중이 크다.

| Phase | 이름 | 대상 | 유형 |
|-------|------|------|------|
| 0 | 기반 준비 | `Room`/`Reservation` 엔티티, H2+JPA 설정, 회의실 시드 데이터 | 스캐폴딩 |
| 1 | 겹침 판정 | `TimeSlot.overlaps()` — BR-01, 2.1 판정표 9케이스 | RGR |
| 2 | 예약 정책 경계값 | `ReservationPolicy` — BR-02~BR-06, `Clock` 주입 | RGR |
| 3 | 예약 생성 통합 | `ReservationService.reserve()` — 겹침+정책 조합, FR-03 | RGR |
| 4 | 예약 취소 | `Reservation.cancel()` — BR-07, BR-08, FR-04 | RGR |
| 5 | 조회 API | `RoomController`, 날짜별 예약 조회 — FR-01, FR-02 | 통합 |
| 6 | API 오류 매핑 | `GlobalExceptionHandler` — 4.3 오류 코드 전체 매핑 | 통합 |
| 7 | 프론트 화면 | 타임슬롯 그리드, 예약 폼, 오류 메시지 표시 — FR-05 | 통합 |

**의존 순서**: 0 → (1, 2 병렬 가능) → 3 → 4 → (5, 6 병렬 가능) → 7. Phase 1과 2는 서로 독립적인 순수 로직이라 순서를 바꿔도 무방하다. Phase 5·6도 서로 막지 않는다.

**시간이 부족하면**: Phase 0은 3에 흡수, Phase 5는 6에 흡수해서 6단계로 압축할 수 있다. 단 Phase 1~4는 이 프로젝트의 시연 목적 그 자체이므로 압축하지 않는다.

## 8. MVP 이후

1. **동시성 제어** — 같은 슬롯 동시 요청. DB 유니크 제약 또는 낙관적 락
2. **로그인** — 예약자명 문자열을 실제 계정으로 교체. BR-07이 제대로 된 인가가 된다
3. **반복 예약** — 매주 월요일 같은 규칙 예약
4. **회의실 관리** — 관리자용 CRUD
5. **알림** — 예약 확정·취소 메일/메신저

## 9. 결정 기록

| 결정 | 대안 | 선택 이유 |
|------|------|-----------|
| 반개구간 `[start, end)` | 폐구간 | 09:00~10:00 직후 10:00~11:00이 정상 시나리오. 경계 테스트가 명확해진다 |
| 취소 = 상태 변경 | 물리 삭제 | BR-08(중복 취소 거절)을 검증하려면 이력이 남아야 한다 |
| `Clock` 주입 | `LocalDateTime.now()` 직접 호출 | 시각 의존 테스트가 실행 시점에 흔들리는 것을 원천 차단 |
| 인증 없음 | 로그인 구현 | 인증이 붙으면 시연 시간의 절반이 인증에 쓰인다. BR-07은 이름 비교로도 시연된다 |
| 동시성 제외 | 낙관적 락 포함 | 재현·시연이 어렵고 RGR 사이클이 길어진다. MVP 이후로 미룬다 |
| 회의실 시드 고정 | 회의실 CRUD | 회의실 CRUD는 로직 없는 CRUD라 TDD 시연 가치가 없다 |
| `POST /{id}/cancel` | `DELETE /{id}` | 취소는 삭제가 아니라 상태 변경이다. DELETE 본문이 중간 경로에서 잘리는 문제도 함께 피한다 |
