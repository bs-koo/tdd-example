# reservation

사내 회의실을 날짜별로 조회하고 예약·취소하는 서비스. 핵심은 **예약 요청을 허용할지 거절할지 판정하는 규칙**이다.

## 배경

이 도메인의 1차 목적은 `/gx-tdd` 파이프라인(PRD → 설계 → RED-GREEN-REFACTOR → 리뷰 → verify → 커밋) 시연이다.

시연 소재를 고를 때 CRUD 중심 서비스(메모장 등)를 먼저 검토했으나 배제했다. `save()`를 부르면 저장되고 `delete()`를 부르면 지워지는 구조에서는 RED 단계에서 쓸 실패 테스트가 "저장했더니 저장됐다" 수준에 그쳐, RGR 사이클이 굴러가는 그림이 나오지 않기 때문이다. 회의실 예약은 `reserve()`가 저장이 아니라 **허용/거절을 결정**하고, 시간 겹침·영업시간·30분 단위·예약 한도 같은 경계값이 자연스럽게 따라온다.

업무 배경은 시연을 위한 **가상 설정**이다: 공유 캘린더와 메신저 구두 예약이 섞여 있어 같은 회의실에 중복 예약이 발생하고, 누가 언제 잡았는지 확인하려면 채널을 여러 곳 뒤져야 한다.

> ⚠️ 위 업무 배경과 아래 규모 수치는 실제 사내 프로세스를 조사한 결과가 아니라 시연용 가정치다.

## 안 하면 어떻게 되는가

시연 목적 기준으로, 판정 로직이 없는 소재를 쓰면 `/gx-tdd`의 핵심 단계가 형식적으로만 지나간다.

- red-writer가 의미 있는 실패 테스트를 만들 수 없다 (GREEN이 너무 쉽게 나옴)
- refactor-coder가 정리할 중복이 생기지 않는다
- spec-reviewer가 판정할 AC가 "저장된다" 한 줄뿐이라 리뷰가 성립하지 않는다

즉 파이프라인은 완주하지만 **TDD가 왜 필요한지가 드러나지 않는다.**

## 성공 기준

| 기준 | 판정 방법 |
|------|-----------|
| 겹침 판정 9케이스가 판정표대로 동작 | `TimeSlot.overlaps()` 단위 테스트 (`@ParameterizedTest`) |
| BR-02~BR-06 경계값이 규칙대로 거절 | `ReservationPolicy` 단위 테스트 (`Clock.fixed()`) |
| 본인 아닌 취소 요청이 403으로 거절 | `Reservation.cancel()` 단위 + API 통합 테스트 |
| 위 규칙이 화면에서 동일하게 동작 | 타임슬롯 그리드에서 수동 확인 |
| `/gx-tdd` 완주 | verify 게이트 0 failures 통과 후 커밋 도달 |
